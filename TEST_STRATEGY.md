# Test strategy playbook

A portable testing strategy for one shape of app: a **static-export frontend
with no backend at all**, whose **only data is what the user imports from
files**, kept **in the browser** (IndexedDB, Cache Storage, `localStorage`),
with a **service worker as the only "server"** (offline shell, share target)
and a **third-party tile server** as the only outside request. It says what
each test layer can and cannot prove in that architecture, and which layer owns
which behavior. Copy it into a new project of the same shape, then localize it
(§16). **This file names no real module, route, file path, or measured
number** — those belong in the project's own docs.

Two meta-rules: **disagree in the open rather than departing quietly** — if a
task needs something this strategy rules out, say so first — and **update this
file the moment the architecture moves**; a stale strategy produces false
confidence at exactly the layer nobody double-checks.

Vocabulary used throughout: the user *imports* *files* (archives, XML
documents) that a *parser* turns into *records*; *pure logic* turns records
into *results* (here: groups, orders, scores); the *data layer* is the one
module family that touches browser storage; the *shell* is the static export
the service worker caches.

---

## 0. When this applies

- The frontend ships as static files. There is **no server runtime, no
  account, no API of its own**; nothing the app holds ever leaves the device.
- All domain data arrives as **files the user chooses** — a file picker, a
  drop, or the operating system's share sheet delivered through a service
  worker. The files are untrusted, however they arrive.
- Persistence is **client-side only**. Clearing site data loses everything;
  there is no second copy to reconcile with.
- The one outside request is a public, unauthenticated resource (map tiles)
  that carries no user data beyond what its URL implies.

If a backend appears — an API, a sync service, an account, a scraper, an
upload of any kind — the central claims (**the parser is the trust boundary**
and **nothing leaves the device**) stop holding. Rethink this document there;
don't patch it.

---

## 1. Purpose

Put each check at the cheapest level that would actually catch the failure it
is aimed at. This needs writing down because there is no server to catch
anything: a parser that misreads a file, or pure logic that drops a record,
fails silently and the interface looks normal while showing the wrong answer.
A strategy that only describes what is already green is not a strategy — name
the gaps (§16).

---

## 2. System testing context

### Map the shape, for the real project

Write this into the project's own docs with its real pieces:

| Piece | Testing consequence |
| --- | --- |
| Static export (no server runtime) | Nothing server-side exists; every behavior is reachable from a unit test or the browser |
| Static host / CDN under a base path | Deployment failures are path failures (base path, asset URLs, manifest, worker scope) — needs a real fetch against the deployed origin |
| Parsers for imported formats (XML, archives) | The trust boundary: hostile, malformed, huge, or merely unusual input lands here first — unit, property, mutation |
| Pure domain logic (geometry, grouping, ordering, scoring) | Where the product's value lives and where silent wrong answers come from — unit, property, mutation |
| Data layer over browser storage | Thin I/O; a schema drift between versions loses data on upgrade — unit with a fake store |
| Service worker (plain script, no bundler) | Its decision functions are unit-tested from source; its lifecycle and interception only in a real browser |
| Web app manifest (install, share target) | A static file nothing imports; a wrong path or field shows only on a phone — source test plus browser check |
| Device APIs (geolocation, wake lock, share sheet) | Permission-gated and absent in CI — faked in unit tests, granted or stubbed in the browser |
| Third-party tile server | Always faked; a test that reaches it is a privacy and flakiness defect |
| CI/CD | Holds no secret of the app's; the highest-privilege thing is the deploy token |

### Trust boundaries to enumerate

1. **Imported file → parser.** Any byte sequence the user can pick or share.
   Not hostile on purpose most of the time, but generated by other tools and
   versions, edited by hand, truncated by mail clients. The parser either
   produces valid records or refuses with a reason; it never produces a
   half-valid record and never hangs.
2. **Share-target POST → service worker.** The operating system hands the
   worker a multipart body; the worker must store exactly the files, under
   names it encodes, and hand control back to the page. A body it cannot read
   is refused, not half-stored.
3. **App → third-party tiles.** The only network egress. Its URL reveals the
   viewed area; nothing else may travel. A content security policy is the
   enforcement; a browser test proves no other origin is contacted.
4. **Device APIs.** A denied permission, a missing API, or an unavailable
   sensor is a normal state, not an error; the feature degrades.
5. **Browser storage across versions.** Data written by build N is read by
   build N+1 with no migration server; an unreadable record must not brick the
   app.
6. **CI/CD → the static host.** Covered by workflow-scanning tools and review,
   not by a test.

## 3. Testing principles

1. **The parser is the security boundary.** Its refusals are features with
   their own tests: wrong format, wrong root, truncated, oversized, too many
   entries, invalid values.
2. **Never mock the thing that carries the risk.** Feed real files (synthetic
   but structurally real) to the real parser; fake only the browser APIs
   around it.
3. **Coverage is a signal; mutation score is stronger.** A line ran proves
   nothing about geometry or ordering logic.
4. **Lowest level with the same confidence.** A distance formula is a unit
   test; *that the map shows a route* is one E2E case, not one per segment.
5. **Deterministic or deleted.** No randomness, no wall clock, no time-based
   iteration limits in logic under test. No retries except the post-deploy
   smoke test, where a retry distinguishes a broken deploy from a dropped
   connection. A flake is a defect.
6. **Test the failure paths.** Import of a partly broken batch, storage that
   refuses a write, a permission denied, a worker that is not there yet.
7. **If it is hard to test, fix the design.** Extract pure logic from the I/O
   beside it; don't fake the world.
8. **Fixtures are synthetic.** Invented names, codes and coordinates that match
   the real format's structure. Never real third-party records, never a real
   person's data.
9. **One new behavior, one new assertion, at one level.**

## 4. Risk model — a template, not a checklist

Rank by expected cost. "Cheapest meaningful test" is the level below which the
risk is uncovered. Replace the rows with the real project's formats, modules,
and operations:

| Risk | Cost | Cheapest meaningful test |
| --- | --- | --- |
| **The parser misreads a valid variant** (another namespace version, another exporting tool) | Records silently missing or wrong; user trusts a wrong answer | Unit with one fixture per variant; property test for invariants |
| **The parser accepts garbage as data** | Nonsense records, `NaN` coordinates poisoning every computation downstream | Unit + mutation on each validation; property: output always valid or a typed refusal |
| **A hostile or huge archive** (entry count, decompressed size) | Tab freezes or crashes; device storage filled | Unit with synthetic archives at and past each limit |
| **Pure logic gives a wrong but plausible answer** (grouping, ordering, scoring) | The product's core claim is false, invisibly | Unit + property + mutation; known-answer fixtures |
| **Non-determinism** (iteration order, randomness, time limits) | Results change between runs; tests flake | Property: same input → same output, input order shuffled |
| **Performance cliff at realistic size** | Unusable on the largest real import | Unit benchmark-style assertion on a generated large input, generous bound |
| **Re-import duplicates or loses records** | Double counting; user state lost | Unit on the merge: idempotent, later wins, local state survives |
| **Storage schema drift between builds** | Data unreadable after an update | Unit on the load path with an old-shaped stored value |
| **Share target delivers nothing or the wrong files** | The main mobile entry point fails silently | Unit on the worker's handler from source; browser check of the manifest |
| **Static-hosting or base-path faults** | A site that quietly breaks post-deploy | Serve the real artifact under its real path, locally and deployed |
| **Stale shell after deploy / offline faults** | Old bundle forever, or no app offline | Unit on cache naming and cleanup; browser check that the worker registers |
| **Data leaves the device** | Privacy breach | CSP source test + browser test that no other origin is contacted |
| **Third-party tile outage** | Map blank; the rest must work | Browser test with tiles failing; unit on the error branch |
| **Device API denied or absent** | Feature crashes instead of degrading | Unit with the API faked away; component test of the fallback |
| **Accessibility regressions** | Unusable with keyboard or screen reader | Static lint + runtime axe — §9 |
| **Untranslated or one-language strings** | Half the users see keys | Parity test over every call site |

Keep 10–20 rows, each marked covered / partly / not covered, updated as
incidents happen.

## 5. Test layers

| Layer | Verdict | Why |
| --- | --- | --- |
| Unit (pure functions) | **Required — the bulk** | Parsers and domain logic are pure; this is where correctness is proven and the only level mutation testing means anything at. |
| Component / hook | **Required** | Hydration mismatches, missing a11y attributes, a control that never disables, a fallback that never renders — invisible to pure-logic tests. |
| Data layer with a fake store | **Required** | Defaults merged in, old shapes read, a refused write surfaced. Thin, but the only place data loss on upgrade is caught. |
| Service-worker logic, unit-tested from source | **Required** | The worker is a plain script; extract its decision functions from the source text and test them like any pure function. |
| Integration with a database | **Not applicable** | There is no database. Browser storage is faked at unit level and real in the browser suite. |
| API / contract testing | **Not applicable** | No API. The import formats are the contract: one fixture per real-world variant. |
| Property-based | **Required, narrow** | Parsers and geometry: an input space nobody enumerates by hand — §10. |
| Mutation | **Required, scoped** | §11. |
| E2E | **Required, small** | §9. Journeys only, through page objects. |
| Dynamic scanning (DAST) | **Not justified** | No server, no headers the host lets the project set, no input reaching a server. A CSP source test covers the one header-like control. |
| Fuzzing | **Property tests stand in** | The parser is the only adversarial surface and is pure; a property test with generated documents is cheaper than a fuzzer harness. |
| Load testing | **Not applicable** | No backend. Client-side scale is a unit-level performance assertion on a large generated input. |
| Concurrency | **Unit level** | In-client races (an import finishing after a newer one started, a stale storage write). |
| Failure injection | **Unit level** | Storage refusing, a file unreadable, a permission denied, through fakes. |
| Deployment | **Required** | The built artifact served under its real base path, locally and post-deploy. |
| Smoke | **Required** | The browser suite against the deployed origin — a Node prerender masks failures only a browser bundle shows. Read-only by construction: there is nothing to write to. |

### Who owns which behavior — and who does not

| Behavior | Owning layer | Not this |
| --- | --- | --- |
| Reading an import format, every refusal | Unit + property + mutation | Not the browser |
| Domain logic (grouping, ordering, scoring, state machines) | Unit + property + mutation | Not the browser |
| Rendering, disabled states, focus, keyboard paths, a11y attributes | Component | Not E2E, unless the journey depends on it |
| What is stored, defaults, old shapes | Data layer unit with a fake store | Not E2E |
| Worker cache naming, cleanup, request classification, share handling | Unit from the worker's source | Not E2E alone |
| Worker registration, offline shell, share target end to end | Browser suite | Not unit alone |
| Base path, icons, manifest, pre-hydration behavior | Browser suite, also post-deploy | Not unit alone |
| No foreign origin contacted | Browser suite + CSP source test | Not review by eye |
| One complete user journey | E2E | Not one case per field |
| Repo tooling outside the bundle | The job that depends on it | Not unit tests, not bundle coverage |

## 6. Architecture-specific strategy

### The shape of the pyramid

Without a backend, the pyramid is bottom-heavy on purpose:

```text
Layer                              Weight           Runs against
---------------------------------  ---------------  --------------------------------
Unit: parsers + domain logic       most of it       pure functions; mutation-scored
Unit: data layer, worker logic     thin band        fakes; worker source evaluated
Component / hook                   a band           jsdom, faked browser APIs
Browser journeys                   one per journey  the built export, tiles faked
Browser smoke                      small            built artifact; also post-deploy
```

Two ways it drifts: logic landing in components where only the browser
reaches it (extract it), or the browser band asserting what a unit test could
have settled.

### What must be real, and what may be faked

| Thing | Unit/component | Browser suite |
| --- | --- | --- |
| Parsers, domain logic | **Real** | Real |
| Import files | **Real files**, synthetic content | Real files, synthetic content |
| Archive library | **Real** | Real |
| IndexedDB / Cache Storage / `localStorage` | Faked (in-memory) | **Real** |
| Service worker | Its functions, from source | **Real** |
| Device APIs (geolocation, wake lock, share) | Faked | Granted, emulated, or stubbed by the browser context |
| Map library | Not mounted in unit tests | Real |
| Tile server | Never reached | **Always faked** at the network layer |
| Ids, clocks | Injected; pure logic takes none | Real |

### Client-only boundaries

- **The parser's output contract.** Every record it returns satisfies the
  types *and* the value ranges (finite coordinates in range, ratings in their
  steps). Downstream logic may then assume validity instead of re-checking.
- **Size and count limits** on archives are checked on declared sizes before
  inflating, and enforced again while inflating. A limit is a named constant
  with a test at the limit and one past it.
- **Storage is a cache of the user's own imports.** Losing it is recoverable
  by re-importing; corrupting it must not be. Load paths tolerate a missing or
  old-shaped value and fill defaults.
- **Determinism is part of the contract** for domain logic: no `Math.random`,
  no wall clock, no time-boxed search; iteration caps are counts.
- **The worker has no import path.** Keep its decisions in small named
  functions so a test can extract and evaluate them; keep its event handlers
  thin.

### Static analysis layering

Four tools answer four different questions; none stands in for another:

1. **Module-boundary graph** (dependency-cruiser): pure logic imports no UI,
   framework, storage or map library; only the data layer imports the storage
   library; only the map wrapper imports the map library; no cycles, no
   orphans; the bundle never imports Node-only tooling.
2. **Dead code / unused dependencies** (knip). Anything referenced only as a
   string in another tool's config, or loaded by the browser by URL (the
   worker), gets an explicit entry point.
3. **Type-aware linting** (typescript-eslint type-checked, jsx-a11y strict).
4. **Code-smell linter** (cognitive complexity, duplication). Tune thresholds
   against the project's own code; a copied default is a guess.

Measure run time before placement: seconds-scale belongs in a pre-commit gate;
a network fetch or cold binary install belongs in CI only.

## 7. Security and privacy testing

**The two properties that matter: hostile input cannot break the app, and
nothing the user imported leaves the device.** No server means no
authorization layer to test; it also means no second line of defense.

### Rules

1. **Every parser refusal has a test**, asserting the refusal's *code*, not a
   truthy error.
2. **Limits are tested at and past the boundary** with synthetic inputs built
   in the test, never large binary fixtures in the repository.
3. **Untrusted strings are rendered as text.** No `dangerouslySetInnerHTML`
   with imported content; a component test renders a record whose name holds
   markup and asserts it appears literally.
4. **The content security policy is source-tested**: `connect-src` allows the
   app's own origin only, `img-src` adds exactly the tile host.
5. **The browser suite fails on any request to an origin other than the app's
   own**, with tiles answered by a local fake.
6. **No credentials, no scraping, no unofficial access** to any third-party
   service exists in the code, so there is nothing of the kind to test; a
   change that adds one invalidates §0.

### Out of scope

Penetration testing the static host; secret scanning beyond a dedicated hook
(the app holds no secrets); the security of the operating system's share
sheet.

## 8. Integration strategy

There is no integration layer in the database sense. What integrates is the
browser: storage, worker, manifest, map. The browser suite covers that, with
these rules:

- **Build the artifact the deploy builds**, and serve it under the same base
  path the host uses. A dev server is never the target.
- **Fake the tile server at the network layer** in a fixture every spec gets
  automatically, so no spec can forget it.
- **Start each test from empty storage.** A fresh browser context per test
  gives that for free; a test that needs prior state creates it through the
  app (an import), not by writing storage directly.
- **Imports in browser tests use small synthetic fixture files** checked into
  the e2e fixtures directory, generated by a script or written by hand,
  never real third-party data.
- **Fail on an unexpected console or runtime error.** This catches a rejected
  background promise hiding behind a passing assertion.
- **Flush browser coverage before every full navigation.** V8 keeps counts
  only for the live document; a reload or `goto` discards everything the test
  did before it.
- **Read function coverage, not line coverage, when deciding what a browser
  suite never reached.** A function at 0 calls is a real gap.

### Idempotency and repeated operations

Every repeatable operation gets a *decided*, tested answer:

| Operation | Decide and test |
| --- | --- |
| Importing the same file twice | Same records, no duplicates; identity is the record's own key |
| Importing an overlapping newer file | The newer record wins; state the user added locally survives |
| Sharing files while the app is open, or twice | Each delivered once, then cleared |
| Starting a guided session that already exists | Resume, or replace on explicit request — never two |
| Clearing all data | Everything the app wrote is gone, nothing else on the origin is touched |

## 9. E2E strategy

One suite, and it is safe everywhere: there is no account and no write that
leaves the browser, so the same specs run against the local export and the
deployed origin. It covers base path, manifest and icons, worker registration,
pre-hydration behavior (language), more than one viewport, and one case per
journey: import a file and see results; open a result and see it on the map;
walk it; change settings; clear data.

A UI change gets one E2E case for its journey; field-level detail (disabled
states, validation wording, focus order) belongs in component tests. Treat
mobile as its own target if layout faults are viewport-specific. Poll for
expected state wherever the UI debounces or waits on a computation.

### How the browser suite addresses the UI

Pick the locator that matches what the test is about, and record the
project's default:

- **Accessible locators** (`getByRole`, `getByLabel`) when the test is about
  what a user sees and does. A control a role-based locator can't find, a
  screen reader can't find either.
- **Stable test ids** (`data-testid`) where they carry a deliberate benefit: a
  repeated card or row, an element whose name is translated or user-supplied,
  an attribute-state assertion (`disabled`, `aria-current`, `lang`), a suite
  that must survive copy edits across locales.
- **Never CSS class or DOM structure.**
- **Text that is the subject is asserted, not located by** — finding an element
  by the text you then assert is circular.
- **A third party's DOM** (a map, an editor) is reached the way it allows,
  inside the page object, with a one-line comment.

**One page object per screen, all hung off one tree.** Each screen exports
`init<Screen>(page)` returning its root locator as a callable, plus `locators`
(grouped handles) and `do` (whole interactions); a repeated row or card gets a
nested object of the same shape:

```ts
export function initResourceList(page: Page) {
  const root = page.getByRole('main');
  const locators = {
    buttons: { newResource: root.getByRole('button', { name: /new/i }) },
    cards: root.getByTestId('resource-card'),
  };
  const interactions = {
    addResource: async (title: string) => {
      await locators.buttons.newResource.click();
      await page.getByLabel(/title/i).fill(title);
      await page.getByRole('button', { name: /save/i }).click();
      await expect(locators.cards.filter({ hasText: title })).toBeVisible();
    },
  };
  return Object.assign(() => root, { locators, do: interactions });
}
```

A tree of getters collects the screens, a fixture hands it to every spec, and
a spec reads as the journey it is:

```ts
test('files a resource and finds it again', async ({ on, page }) => {
  const app = on(page);
  await app.resources.do.addResource('Title');
  await expect(app.resources.card('Title').locators.title).toHaveText('Title');
});
```

Four rules keep this from decaying:

- **No spec names a selector.** Grep the spec directory for `getByTestId`,
  `getByRole`, `locator(`; only document-level elements (`html`, `body`,
  `meta`, `link`) may show up.
- **`do` holds whole actions; `locators` holds handles.** An action spanning
  two screens belongs to the screen that starts it.
- **Waiting belongs to the page object.** `open()` returns when the screen is
  there, not when the click landed. No spec carries a sleep.
- **Assertions belong to the spec.** A page object asserts only its own
  action's postcondition.

### Device APIs in the browser

Grant or deny a permission per browser context; set a fixed emulated position
for geolocation. A spec about the fallback denies the permission rather than
faking the API's internals. The share sheet itself cannot be driven; a
`multipart/form-data` POST to the share-target URL, issued from the page
context once the worker controls it, stands in for it.

### Accessibility

**Static** (a JSX a11y linter) catches missing alt text, invalid ARIA, an
unlabeled control before anything renders. **Runtime** (axe-core in the browser
suite) catches computed contrast, real focus order, accessible-name computation
— on representative states, not every route. Decide which severities block;
treating every finding as blocking gets the gate disabled the first time it
catches something ambiguous. Neither proves compliance or screen-reader
behavior: a clean run is "no known regression," and the docs say so.

## 10. Property-based testing strategy

**Narrowly, but earlier than in a backend app**: here the parser and the
geometry are the whole risk surface, and both have properties that are easy
to state.

- **Parsers:** for any generated valid document, every record parses with the
  values that went in; for any generated document, the output is either valid
  records or a typed refusal — never an exception of another kind, never a
  non-finite number.
- **Geometry:** distance is symmetric, zero on identical points, and obeys the
  triangle inequality within floating-point tolerance; bearings stay in range.
- **Domain logic:** results do not depend on input order; every output item
  traces back to an input that passed the filters; limits (size, length) hold
  for every result.
- **Merges:** idempotent, and associative where the design says so.

Seeded and deterministic, one dependency, beside the example tests rather than
replacing them, inside the unit suite's time budget.

## 11. Mutation testing strategy

**Required, scoped — never the whole codebase.**

- One short, explicit file list, shared with the per-file coverage floor so the
  two can't drift.
- Every listed file is pure logic, or I/O reached through an injected parameter
  so a test can drive it and assert the request it composed. Prefer that over
  exclusion regions; any exclusion carries its reason at the exclusion.
- **Never mutate the rendering layer.** JSX mutants are near-equivalent by the
  thousand. A file that can't split into logic and rendering is the problem.
- Run on every change touching scoped files. A scoped run is fast; learning
  after the merge that a test asserts nothing is too late.
- Incremental reuse of earlier results is fine on a change, provided the
  branch that deploys reruns everything: the tool's diff sees mutated code and
  tests, not what the mutated code imports, nor a dependency bump. Key the
  saved results on what it cannot see.

A surviving mutant has two honest endings: **a missing assertion** (kill it
with a real behavioral test, usually an unpinned boundary or error path), or
**equivalent**. For an equivalent mutant, first ask whether the code needs to
exist — a guard the type system already discharges, a default spelled out, a
wrapper every caller unwraps. Deleting that code is the ending that pays for
the exercise. What genuinely remains is left visible in the report with its
reason written down, never hidden behind a suppression. Never write a test that
can't fail just to kill a mutant.

Two structural survivor classes worth knowing: in React, an empty dependency
array (the tool replaces it with a constant React reads as unchanged — drop the
memoization if it isn't load-bearing, otherwise leave the survivor visible);
and in iterative algorithms, a timeout (a loop bound or iteration cap driven
past its end — bound loops by the data, and make caps counts the tests can
reach).

Below threshold fails the build. Above threshold but below 100% is not a pass;
every survivor is an open question.

## 12. Performance and resilience testing

### Performance

**No backend, so no load test.** The performance risk is the client doing too
much work on the largest realistic import. Address it where it lives:

- Algorithms over the imported records name their complexity; anything that
  compares records pairwise uses a spatial index or equivalent, never all
  pairs.
- A unit test runs the core pipeline on a generated input at the largest
  realistic size and asserts it finishes within a **generous** bound (an order
  of magnitude above the measured time), to catch a complexity regression,
  not to benchmark.
- Iteration caps in optimizers are counts, so the result and the run time are
  both deterministic.

A frontend budget (Lighthouse or similar) is optional; adopt it from a
measured baseline with margin if bundle size starts to matter on phones.

### Resilience

Failure injection at unit level, through fakes the modules already accept:
storage that refuses a write or returns an old shape; an archive entry that
fails to inflate; a batch import where one file is unreadable (the others
still import, the bad one is reported); a permission denied; a worker that has
not taken control yet.

## 13. CI/CD execution strategy

1. **Fast hygiene first** — file hygiene, secrets, formatting gate everything
   else, so a bad config fails before minutes are spent on browsers.
2. **Path-filter heavy jobs on PRs.** A job skipped by its own condition
   reports as passing and never weakens branch protection.
3. **Full, unconditional set on the branch that deploys**, whatever the push
   touched, and the deploy starts only once that run has passed on the same
   commit.
4. **Deploy pipeline fails safe**: build, verify the artifact exists, deploy,
   smoke-test against the live origin — each depending on the last.
5. **Retry only the deploy-target smoke test.** Everywhere else `retries: 0`.
6. **No secrets needed** beyond the platform's own deploy token; a job that
   asks for one is a design change.

**Scheduled jobs:** dependency updates — auto-merge patch-level bumps at most,
and only of packages the build that produces the deployed artifact never runs.
Keep build tools out of the dev section, install without lifecycle scripts,
and gate auto-merge on the resolved lockfile.

## 14. Quality gates

Every gate needs a stated reason; a gate without one gets loosened the first
time it is inconvenient.

| Gate | Guidance |
| --- | --- |
| Coverage floor | A **floor** set from what the suite achieves, with margin — not a target. Raised by hand. One floor for the unit suite (with a stricter per-file floor on the mutation list) and one for the browser suite. |
| Auto-ratcheting coverage | **No.** It makes a green local run produce a red PR. |
| Mutation score | A break threshold just below the measured score, so one new equivalent mutant can't block unrelated work. Survivors above it remain open questions. |
| Any threshold | **Never lowered** to pass a build. Redesign, or raise the question. |
| Gate scope | A gate is required when the diff touches its inputs. Comments, docs and file moves produce no new mutant or bundle, so the gates that read those inputs are not required for such a change; CI's path filter is the executable form of the same rule. |
| Test pass rate | 100%, `retries: 0` except the deploy-target smoke test. |
| Privacy | CSP source test and the no-foreign-origin browser check stay green. |
| Translations | Every call site's key exists in every language; both dictionaries declare the same keys; no key is unused. |
| Deployment | Post-deploy smoke green against the **live** origin. |
| Static analysis | Block on real findings, surface the rest (§6). |
| Suppressions | Only with the reason written at the suppression, after understanding the failure. |
| New UI | An E2E case for the journey, component coverage for field detail. |
| New behavior | A unit test; parser or domain logic additionally a property where one is easy to state. |

## 15. Test anti-patterns

Each of these passes silently or looks like flake when it is a defect.

1. Real third-party records or personal data in a fixture.
2. A test that reaches the real tile server, or any other origin.
3. Mocking the parser or the archive library in a test about importing.
4. Randomness, the wall clock, or a time limit inside logic under test.
5. Asserting a result's count instead of its contents on a known fixture.
6. Pure logic re-tested through the browser.
7. A browser test that seeds storage directly instead of importing through the
   app.
8. Retries or sleeps to paper over a flake.
9. A threshold lowered, or a suppression added, to get to green.
10. A test written to touch a line, a branch added to dodge a mutant, a file
    excluded to avoid dealing with it.
11. Mutation scope widened to the rendering layer.
12. A truthiness check on an error object instead of its code.
13. An E2E case for a field-level detail.
14. An element located by CSS class, DOM position, or the text the test then
    asserts.
15. A large binary fixture committed to test a size limit a generated input
    would reach.

## 16. Adapting and maintaining this playbook

**Copying into a new project:** fill §2's table and boundaries; build §4's
risk table with real formats, modules, and operations; fill §5's ownership
table once real modules exist; pick §6's four static-analysis tools and §11's
mutation scope; record §9's default locator strategy; measure §12 and §14's
thresholds — never carry another project's numbers. The instantiation goes in
the project's own docs (architecture, design decisions, CI config, pre-merge
checklist), never into a copy of this file.

**Update it when:** a backend, account, sync, or upload appears (invalidates
§0); a new trust boundary appears (another import format, another device API,
another third-party request); a §5 verdict changes (record the reasoning); a
gate moves (a changed number is a changed justification); a named gap closes
(delete it); or an incident happens — add it to the risk model and name the
level that should have caught it.
